Working prototypes · one synthetic dataset

Going from a number to the reason for it.

Drill-down is the whole distance between a summary a manager can read and the individual records that produced it. There are twelve well-known ways to travel it, plus a thirteenth that is never on the list and is the first thing anyone asks for. Every one is a live prototype below — not a screenshot.

All twelve run against the same generated fact table for Meridian Outdoor Supply, a fictional retailer, built in your browser when this page loaded. The roll-ups are computed, not typed in, so if a total looks wrong you can drill into it and find out why.

Architecture

What actually happens when someone clicks a bar

A drill click is not a UI event that stays in the UI. It becomes a parameterised query against a governed engine, and everything hard about drill-down lives in the three hops between the two. This is the shape I'd build.

Group one of four

Navigate — move to a different place in the data

The techniques are grouped by what they do to the query, not by how they look, because that grouping is also the one that predicts where the work has to run. Navigation changes the grain: you end up looking at a different set of rows than you started with.

01Navigateruns on the API

Hierarchical drilling

Descend a declared hierarchy one level at a time. Region → Country → City. Each level is a separate query with the parent's value bound in as a predicate.

CostThe hierarchy has to be declared somewhere. Data alone cannot tell you that Vancouver rolls into Canada rolls into North America — that is a modelling decision, and if it drifts from the warehouse the drill silently returns nothing.
06Navigatehits the fact table

Drill-through to source records

Skip the levels entirely and jump from an aggregate straight to the individual rows behind it. Click a KPI, get the transactions.

CostThis is the only technique that returns un-aggregated rows, so it is the one that leaks. A summary of orders is harmless; the orders themselves name customers. Row-level policy has to hold here or nowhere.
08Navigateclient + API

Zoom and level-of-detail

Narrow the window and let the grain follow it. A year of data is drawn by month; a fortnight of the same data is drawn by day, without anyone choosing a grain.

CostAutomatic grain is the friendliest of the twelve and the easiest to get wrong. The switch must be announced, or the same chart quietly changes what a bar means and people compare a daily bar to a monthly one.
Group two of four

Constrain — keep the grain, shrink the set

These three all end up as a WHERE clause. They differ in who writes it: the user picks a dimension value, types a threshold, or clicks a mark in another chart and lets the system infer it.

02Constrainruns on the API

Slicing and dicing

A slice pins one dimension to one value. A dice pins several at once, carving a sub-cube. The grain never changes — only how much of the cube you are looking at.

CostDicing hard enough produces cells with three rows in them, which then get shown as a trend. Small-cell suppression is not optional once anyone makes a decision from the result.
03Constrainruns on the API

Filtering by measure

Not a dimension value but a condition on the number itself: show only the cities above a revenue floor. This is a HAVING, applied after aggregation.

CostA measure filter changes the denominator of everything downstream. If the page still shows "share of total" after filtering, decide once whether total means the filtered set or the whole — and label it.
07Constrainclient-side

Linked views and cross-filtering

Selecting in one chart constrains every other chart on the page. One gesture, one predicate, broadcast to every widget bound to the same dataset.

Revenue by month — click a column
Channel — click a chip
Category — click a bar
CostEvery chart on the page becomes a query on every click. Three widgets is three queries per selection; a fifteen-widget dashboard is a stampede. Debounce, batch into one request, and cache by predicate set.
Group three of four

Arrange — same rows, different shape

Nothing here changes which records are in play. These techniques change the GROUP BY, the ORDER BY, or which dimension is on which axis — and that is often the entire difference between a table nobody reads and an obvious answer. This family also holds the thirteenth technique, which is the one everybody asks for by name: grouping the data their own way, and then expecting the drill to follow it down.

04Arrangeclient under 10k rows

Sorting and grouping

Choose the grouping key, then order by any measure. Sorting by margin rather than revenue is usually where the interesting question starts.

CostMargin % is the trap. It is a ratio, so it cannot be summed or averaged up the hierarchy — it has to be recomputed from stored numerator and denominator at whatever level is on screen. Averaging the children gives a plausible, wrong number.
13Arrangeruns on the APInot on the standard list

Logical grouping — and whether the drill follows it

Sets a user defines themselves, cutting across the declared hierarchy: sales blocs, order-size bands, revenue quintiles. Whether you can drill into one is not a UI question — it depends entirely on what decides membership.

Edit the mapping — your blocs become a real dimension in the workbench below
AnswerYes for the first two, no for the third — and the demo computes the difference rather than asserting it. Change the filter and watch how many members move between groups. A grouping fixed before the query behaves exactly like a declared level; a grouping derived from the aggregate is redefined by every filter the drill applies.
05Arrangeruns on the API

Pivoting and cross-tabulation

Put one dimension on rows, another on columns, a measure in the cells. Swapping the axes asks a genuinely different question of the same numbers.

CostColumn count is user-controlled and therefore unbounded. Pivot City against Item and you have asked for 400 columns; the query succeeds and the page dies. Cap the column dimension's cardinality before the query, not after.
09Arrangeengine-side

OLAP cube operations

The formal vocabulary the other techniques are informal versions of: drill-down, roll-up, slice, dice, pivot, rotate. Each is a transform on a cube address, and the sequence is replayable.

CostThe vocabulary is the easy part. Making the six operations closed — every operation valid from every state, and every state addressable — is where cube engines earn their licence fee.

      The honest part
      
Where this gets hard

      
None of the twelve is difficult on its own. What makes drill-down an engineering
        project rather than a feature is that correctness, latency, security and cost all degrade in
        different directions as depth increases — and the first three of these produce wrong answers
        rather than errors, which is worse.

    


    

      
Correctnesssilent

        
Ratios and distinct counts do not roll up

          
A 42% margin and a 61% margin do not combine into 51.5%, and two regions with 900 unique
            customers each do not make 1,800. Averaging children is the single most common drill-down bug
            because it always returns a plausible number.

          
MitigationStore and transport the numerator and denominator separately.
            Compute every ratio at the level being displayed. Never let a ratio column be aggregated by the
            generic roll-up path.


      
Correctnesssilent

        
Mixed grains in one table double-count

          
When a table stores both the parent level and the child level as rows — a region total sitting
            alongside its cities, a 2-digit product code alongside its 4-digit children — a naive
            SUM counts the same money two or three times. The query succeeds; the total is
            simply inflated.

          
MitigationNever expose the union table to the query builder. Publish one
            view per grain, each pre-filtered to its own level, and make those views the only thing the
            drill resolver can name.


      
Correctnesssilent

        
Custom groups defined by a measure move underneath the drill

          
"Top quarter of cities", "high-margin items", "at-risk accounts" — groups whose membership is
            computed from an aggregate rather than mapped from a dimension. Drilling applies a filter, the
            ranking is recomputed against the surviving rows, and the group silently changes who is in it.
            The user clicked "Top quarter" and is now looking at a different top quarter. Prototype 13
            measures the movement.

          
MitigationResolve membership once, at the level the user selected, and
            carry the resulting member list down the drill as an explicit predicate. If membership must
            stay dynamic, say so on the chart — a group that re-ranks is a filter, not a level, and it
            cannot be pre-aggregated.


      
Performancecompounds

        
Latency multiplies with depth

          
Four levels is four sequential round trips, because level n's predicate is not known
            until level n−1 is clicked. At 300 ms each that is 1.2 seconds of dead interface spread
            across a gesture the user experiences as one action.

          
MitigationPrefetch the children of the focused mark on hover or focus.
            Keep the previous level on screen, dimmed, rather than swapping in a spinner — perceived latency
            is what is actually being fixed.


      
Performancecliff

        
Cardinality bombs

          
Drilling into City returns 400 rows. The identical gesture on Customer returns 2.4 million.
            The interface offers no clue which one is about to happen, and the chart component will happily
            attempt to render both.

          
MitigationStore distinct counts per level in the catalogue and refuse to
            render a level above the cap. Substitute a searchable, paginated list for the chart, and always
            bucket the tail into "other" rather than truncating it silently.


      
Costgrows

        
Pre-aggregates explode combinatorially

          
Four dimensions of three levels each imply 256 possible cuboids. Materialising all of them is a
            nightly job that costs more than the dashboard, and materialising none of them means every top-level
            page load scans the fact table.

          
MitigationMaterialise from observed click paths, not from the schema. Log
            which (dimension, level, filter) combinations are actually requested, build those, and retire any
            summary whose hit rate falls below a threshold.


      
Securitybreach-class

        
Authorisation has to survive the last hop

          
Aggregates are usually safe to show broadly; the records underneath them are not. Drill-through
            is the one technique that crosses that line, and a result cache shared across sessions will
            happily serve one user's rows to another.

          
MitigationEnforce row-level policy in the engine, below both the summary
            and the fact table, so no API path can bypass it. Key every cache entry by principal as well as
            by query, and re-check on every hit.


      
Securityinjection

        
Drill parameters are user input wearing a chart's clothes

          
The value bound into the next level's predicate arrived from a click handler in a page the user
            controls. It is exactly as trustworthy as a form field, and it is being interpolated into SQL.

          
MitigationCoerce to the declared type, check against a character allowlist,
            escape as a literal, and run the session read-only with a statement timeout. Four independent
            layers, because any one of them can be wrong.


      
Usabilitychronic

        
Depth without a trail loses people

          
Three levels down, cross-filtered twice and re-sorted, a user cannot say what they are looking
            at, cannot get back, and cannot send it to anyone. The finding exists only in their tab.

          
MitigationTreat drill state as an addressable resource: the path, filters,
            grain and sort all serialise into the URL, browser Back rolls up exactly one level, and a
            breadcrumb is on screen at every depth.


      
Usabilityexcludes

        
Half of these idioms assume a mouse

          
Hover-to-preview, click-a-tiny-mark and brush-to-zoom all fail on touch, and a chart drawn as
            SVG paths is invisible to a screen reader and unreachable by keyboard — which quietly makes the
            drill-down feature unavailable to part of the audience.

          
MitigationEvery drillable mark is a real focusable control with an
            accessible name carrying its value. Tap drills, an explicit control rolls up, and the same data
            is available as a table. Every prototype on this page follows that rule — try it with Tab.


      
Costunbounded

        
Curiosity is billed per query

          
On a consumption-priced warehouse, a cross-filtered dashboard turns one idle click into a dozen
            scans. There is no natural ceiling, because the interface rewards exploration and the invoice
            arrives a month later.

          
MitigationCache on the full predicate set, batch a page's widgets into one
            request, and give each dashboard a query budget with a visible degradation mode rather than a
            surprise bill.

Build order

      
These phases are sequenced by dependency, not by visible value: each one is the thing
        that has to be true before the next is safe to attempt. Each ends with something demonstrable.

    • 
          
  • Drill state in the URL from day one — retrofitting it is painful

    •

Proves: the invoice stops scaling with curiosity

      

    

  






  

    
About the data. Meridian Outdoor Supply is invented. Its fact table is generated
      deterministically in your browser from a fixed seed when the page loads, with seasonality built into
      the product mix — snow sells in Q1 and Q4, paddle in Q2 and Q3 — so the prototypes have real patterns
      to reveal rather than noise. Nothing is fetched and nothing is sent anywhere.

    
About the timings. The only numbers on this page that are modelled rather than computed are
      the latency figures in prototype 11, which apply a fixed scan rate to the true row counts. Everything
      else — every total, every roll-up, every cell — is calculated from the generated rows at the moment
      you interact with it.
